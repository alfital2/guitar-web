## 2026-07-01T22:45:00Z — performance-profiler
Task was "measure sustained idle GPU/compositing cost — fans spin from continuous background animation, not load metrics." The entire performance-profiler.md reference is Web-Vitals oriented (LCP/CLS/TBT/FCP/TTFB) and provides ZERO scripts or guidance for: CDP Tracing category breakdown (Scripting/Rendering/Painting/Compositing/GPU), frame-production rate while idle (DrawFrame/s), LayerTree composited-layer inventory, or per-thread busy time (CrGpuMain/VizCompositor/Compositor). Had to hand-write a playwright-core CDPSession tracer. Key traps found the hard way: (1) an in-page rAF fps probe forces a main-thread frame every vsync and completely pollutes the "scripting vs compositor" answer — must read frames from DrawFrame trace events instead; (2) summing every 'X' event dur per thread double-counts nested slices — need interval-union for true busy time; (3) a compositor-driven CSS transform animation produces 120 GPU frames/sec at ~16% GpuMain busy with 0% scripting/raster, which no Web-Vital would ever surface.
**Suggested change:** references/performance-profiler.md — add an "Idle / animation cost profiling" section with a CDP Tracing recipe (includedCategories for devtools.timeline+cc+gpu+viz+disabled-by-default-devtools.timeline.frame), interval-union busy-time-per-thread analysis, DrawFrame/s frame-rate measurement, and LayerTree composited-layer inventory. Note the rAF-probe contamination and nested-slice double-count pitfalls.
